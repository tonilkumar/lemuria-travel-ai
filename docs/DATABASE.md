# Database

PostgreSQL 17. Schema in `apps/api/src/db/schema/`, one file per module.
Migrations are generated by drizzle-kit into `apps/api/drizzle/` and applied
explicitly — never on server boot.

Current: **57 tables, 13 enums, 110 indexes, 107 foreign keys.**

## Money

Every monetary column is `bigint` holding **integer paise** (1 rupee = 100
paise), via the `money()` helper in `_shared.ts`.

Floats are never used. A quotation applies a supplier cost, other costs, a
markup and GST in sequence; binary floating point drifts under that chain and
the drift becomes real rupees on the invoice. `bigint` also clears `integer`'s
~₹2.1 crore ceiling, which a group booking can exceed.

Percentages that feed money are stored in **basis points** (`markup_bps`,
`gst_bps`, `margin_bps`) for the same reason — `1875` means 18.75%.

The frontend formats paise to rupees at the edge and does no arithmetic on them.

## Identity and duplicates

Customers and leads both carry `name_normalised` — lowercased, accent-folded,
salutation-stripped — alongside indexed `phone` and `email`. Duplicate detection
matches on phone, email, name+phone and name+email, and grades confidence: a
shared phone or email is MEDIUM, a name plus one of them is HIGH. A name alone
never counts; "Priya Sharma" is not rare.

Candidates are **surfaced, never merged**. The user chooses use-existing,
create-anyway, or opens the record.

Human-readable codes (`LM-L-2026-000123`) come from the `code_sequences` table
via a single atomic upsert (`ON CONFLICT DO UPDATE ... last_value + 1`), so two
executives filing an enquiry in the same instant cannot be handed the same code.
This requires the unique index on `(scope, year)` — without it the upsert has no
conflict target and silently inserts duplicate counters.

## Soft delete

Business tables carry `deleted_at`. Rows are never hard-deleted, because the
audit trail must stay resolvable to the entity it describes. Queries filter
`deleted_at IS NULL`; the unique index on `users.email` is partial on the same
predicate, so an address can be reused after a soft delete.

## Audit

`audit_logs` is append-only. The application issues no UPDATE or DELETE against
it, and production revokes those grants so an application bug cannot rewrite
history. Entries store a field-level diff rather than two full snapshots, and a
redaction list drops secrets and full ID numbers before write.

Audit writes take the caller's transaction, so an entry can never survive a
rolled-back change.

`document_access_log` records every **read** of a document, not just writes —
passport and identity scans need a who-looked-at-this trail.

## Master data vs enums

Postgres enums (structural — code branches on them): lead status, lead
classification, follow-up status and type, priority, customer tier, document
type, quotation status, visa workflow step, passport application type,
communication channel and direction, AI review status.

Master-data tables (admin-editable, no branching): `lead_sources`,
`travel_types`, `destinations`, `visa_countries`, `visa_types`,
`visa_checklist_templates`, `payment_methods`, `supplier_types`, `settings`,
`notification_templates`, `communication_templates`.

Visa checklist items are **copied onto the case** at creation. Editing a country
template later must not rewrite the requirements of a case already in flight.

## Indexing

Indexes serve specific screens, not speculation:

- `leads_status_created_idx`, `leads_assigned_status_idx`,
  `leads_classification_idx` — the Leads workspace tabs and default sorts.
- `leads_next_followup_idx` — the overdue / today / upcoming filters.
- `followups_assigned_status_due_idx` — the personal work queue.
- `customers_phone_idx`, `customers_email_idx`,
  `customers_name_normalised_idx` — duplicate detection, hit on every enquiry.
- `documents_expiry_idx`, `customer_passports_expiry_idx` — expiry alert sweeps.

`pg_trgm` and `unaccent` are created by the migrate script for fuzzy search.

## Two traps worth knowing

**Optional filters and PREPARE.** Build them by appending conditions only when
the value is present, as `buildLeadFilters` does. Passing a NULL parameter into
an optional range comparison leaves Postgres unable to infer the parameter's
type, and the statement fails at PREPARE — before any row is examined — with a
confusing `42P18 could not determine data type of parameter`.

**Resetting the database.** Dropping only the `public` schema is not enough.
Drizzle keeps its migration journal in a separate `drizzle` schema, so the next
`db:migrate` sees the migration as already applied and no-ops against an empty
database, and the first query then fails with `relation ... does not exist`. Use
`pnpm --filter @lemuria/api db:reset`, which drops both.
